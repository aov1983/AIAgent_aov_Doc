# Запрос администраторам стенда n8n: поднять лимит JS Task Runner

**Стенд:** ai-test.develonica.group (n8n **2.21.2**, self-hosted, внешний JS task runner)
**Дата:** 2026-06-26
**Суть одним предложением:** дефолтный лимит выполнения Code-ноды в **60 секунд** не даёт использовать мощные LLM для извлечения требований — просим поднять его до **600–10800 секунд**.

---

## Что просим изменить

Переменную окружения **`N8N_RUNNERS_TASK_TIMEOUT`** (значение в **секундах**) для контейнера, который запускает JS task runner:

```
N8N_RUNNERS_TASK_TIMEOUT=600        # минимум (10 минут); рекомендуется 3600–10800
```

- **Текущее значение на стенде:** не задано → действует дефолт **60**.
- **Рекомендуемое:** **10800** (3 часа) — ровно так настроено на нашем dev-хосте (см. `n8n/compose.yaml:147`), проверено на больших документах.

Где задаётся (n8n 2.x с внешними task runners): в `environment` сервиса, исполняющего раннер (`task-runner-javascript`), или прокидывается из сервиса `n8n` в раннер — зависит от вашей сборки compose. Пример из нашего `compose.yaml`:

```yaml
    environment:
      # JS Task Runner: один Code-таск обрабатывает весь документ по чанкам через LLM.
      N8N_RUNNERS_TASK_TIMEOUT: "10800"
```

Документация n8n: переменные раннера `N8N_RUNNERS_*` (Task runners → Configuration).

---

## Почему это блокирует работу (технический корень)

Пайплайн извлечения требований (`wf_api_documents`, нода `[upload] Merge Chunks`) обрабатывает документ **по чанкам внутри одной Code-ноды**, делая по каждому чанку 2 вызова LLM (extract + decompose). Время чанка целиком определяется **скоростью генерации (decode) выбранной модели**.

- На **лёгкой** модели `Yandex-qwen3.6-35b-a3b` (3 млрд активных параметров MoE) один чанк ≈ 21 с → укладывается в 60 с → документ обрабатывается **полностью** (234 требования, статус `completed`, ~14 мин).
- На **мощной** модели `Yandex-qwen3-235b-a22b-fp8` (22 млрд активных) decode в ~7–10 раз медленнее; плотный чанк (extract+decompose) **превышает 60 с** → раннер обрывает ноду с ошибкой:

```
Task execution timed out after 60 seconds
  at JsTaskRunner.taskTimedOut (/opt/runners/task-runner-javascript/dist/task-runner.js:234:25)
```

В результате на мощной модели документ обрабатывается **частично** (`partial`), большинство требований теряется.

## Что уже перепробовано на стороне приложения (не помогло)

Чтобы показать, что вопрос не решается настройками воркфлоу:

1. **Снижение параллелизма** (`conc=1`) — обязательно для тяжёлой модели, но недостаточно.
2. **Внутренний watchdog прохода** (`pass_budget_ms`, по умолчанию 45 с < 60 с) — спасает ноду от падения, но обрывает обработку чанка на полпути.
3. **Дробление чанков** (уменьшение размера) — имеет оптимум и **за ним деградирует**: при дроблении ×2 — 39 требований, при ×3 — уже 9 (накладные расходы петли съедают время).

Все рычаги уровня приложения исчерпаны. Единственное узкое место — **жёсткий лимит 60 с на уровне инфраструктуры раннера**, который из воркфлоу не обойти.

---

## Эффект от изменения

- Откроется использование мощных моделей (qwen3-235b и крупнее) для извлечения требований — полная обработка вместо `partial`.
- Обработка таких моделей будет медленнее (десятки минут на документ), но **полной**.
- Лёгкие модели работают как прежде.

## Риски

Практически отсутствуют для пакетной обработки: единственное следствие — реально «зависшая» Code-нода (бесконечный цикл, мёртвый внешний сервис) будет жить до нового лимита, а не до 60 с. Для нашего пайплайна это приемлемо (есть собственный watchdog и ограничение числа проходов).
